# Interview and approval protocol

## Grill-Me Style Interactive Protocol

The interview part of Project Memory operates in an interactive "Grill-Me" style:

1. **One Question at a Time**: Walk down each branch of the design tree sequentially, resolving dependencies between decisions step-by-step.
2. **Propose Recommended Answers**: For every question, inspect the repository/codebase evidence first and provide a recommended answer prefixed with `(Recommended)`.
3. **Use Interactive Question Tools**: Use interactive selection UI tools (`memory_ask` in Pi or `ask_question` in Antigravity) with selectable choices and default options.
4. **Codebase Exploration First**: If a question can be answered by exploring the existing codebase, explore the codebase instead of asking.
5. **Incremental Persistence**: Save confirmed answers into `.memory/goal.md` and sync `AGENTS.md` via `memory_apply` after each round.

## Multi-Round Iterative Interview Protocol

Interviews MUST be multi-round and iterative (at least 3 to 4 rounds) to ensure complete clarity before finalizing goals:

- **Round 1 (Foundation ~10 decisions, asked one-by-one):** Focus on core objectives, users, scope, key features, and constraints. MUST include:
  - **Feature Classification & Directory Location:** Always ask whether this is a **new standalone feature** or an **add-on feature** to an existing system, and whether to create a new folder/scope directory or use an existing folder.
  - **Design Patterns & Architecture:** Always ask what specific **design patterns** (e.g. Repository, Factory, Strategy, MVC, CQRS, Clean Architecture) and repository organization principles the user wants used for designing the codebase before implementation. (Consult `software-design-patterns` skill).
- **Round 2 (Clarification 5–10 decisions):** Based on Round 1 answers, ask targeted follow-up questions to resolve ambiguities, edge cases, data flows, and non-goals.
- **Round 3 (Refinement ~5 decisions):** Pin down exact must-not rules, error handling, preferences, and acceptance criteria.
- **Round 4+ (Final Polish):** Address remaining edge-case questions until every requirement, directory location, design pattern, and constraint is crystal clear.
- **Final Synthesis & Approval:** Present the structured synthesis and obtain explicit user approval before moving the goal state to `ready`.

## Mandatory Interview Topics (Must Ask)

1. **Feature Type:** Is this a new standalone feature or an add-on to an existing feature?
2. **Directory / Scope Location:** Should a new folder be created for this feature scope, or should an existing folder be used?
3. **Design Patterns & Architecture:** What design patterns (e.g., Factory, Strategy, Repository, Clean Architecture, MVC) and structural conventions should be followed? (Consult the `software-design-patterns` skill to evaluate trade-offs and record confirmed choices in `goal.md` and `AGENTS.md`).

## Project interview: 10–20 decisions

Cover relevant users, problem, outcome, success, workflows, scope, feature classification, directory scope, design patterns, non-goals, priorities, data, integrations, security, privacy, accessibility, reliability, performance, architecture constraints, testing, deployment, migration, rollback, deadlines, risks, and completion.

## Feature interview: 10–15 decisions

Cover feature type (new vs add-on), directory/folder location, design patterns, actor, trigger, outcome, happy path, inputs, outputs, state transitions, UI/CLI/API behavior, failures, permissions, privacy, accessibility, dependencies, functional/non-functional requirements, preferences, must-not rules, acceptance criteria, operations, migration, compatibility, rollout, rollback, and completion evidence.

## Approval gates

Explicit approval is required for project interpretation, tracked scopes, goals, acceptance criteria, material intent changes, preference reversals, unapproved architecture/scope changes, completion, and reopening. Silence, code presence, tool success, or confidence is not approval. Semantic plans also carry a confirmation token generated by the host UI or tied to a stable user-message reference; never fabricate one.

After completing the interview and applying the approved goal update, evaluate whether the repository root `AGENTS.md` should be updated to reflect newly confirmed coding guidelines, constraints, or architecture decisions. Ensure any edits to `AGENTS.md` preserve the managed `<!-- memory:start --> ... <!-- memory:end -->` block.
